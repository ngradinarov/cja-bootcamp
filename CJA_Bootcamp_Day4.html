Section 1

Data views deep dive

The layer between the raw data and everything you have built this week.

Divider.

Data views

What a data view controls, and what it cannot

IT DECIDES

  • Which components exist, and what they are called
  • Whether a field is a metric or a dimension
  • Attribution, persistence, bucketing, formatting
  • Session definition and timeouts
  • Which values are included or excluded

IT CANNOT

  • Add data that was never collected
  • Change which datasets are in the connection
  • Fix an identity that was never captured
  • Read free text and tell you what it means
Everything on the left is reversible and retroactive. Everything on the right needs a conversation with whoever owns collection, and a wait.
Five minutes. The two column framing is the triage tool from the warm-up, made explicit. The right hand list is the honest boundary and the last item is this morning's whole exercise, so plant it here.

Data views

Connection, data view, project

Connection
Which datasets are in play, their types, backfill and stitching. Changing it affects every data view built on it. Administrator territory.
Data view
How those datasets are interpreted. Components, names, attribution, session rules. Many data views can sit on one connection and disagree with each other legitimately.
Project
One person's analysis. Segments, calculated metrics, column overrides. Changing it affects nobody else.
Derived fields are the exception. They are built inside a data view but managed at connection level, so a change in one data view reaches every data view on that connection. That surprises people, including people who have used this for years.
Five minutes. The derived field exception is important, exam relevant and genuinely counter-intuitive, so give it the callout and repeat it when you get to the derived fields section. It is also why everyone has their own data view but shares a connection: their derived fields will collide unless they name them properly.

Data views

Containers, and where components live

  • The default container model is person, session, event, the same three you have used all week.
  • Components are assigned to a container when they are added to the data view.
  • A component in the wrong container produces results that look plausible and are wrong, which is worse than an error.
  • You can also define custom containers from objects or arrays inside an event, which unlocks sub-event analysis.
Plausible and wrong is the failure mode to fear in this tool. An empty report gets investigated. A believable one gets presented.
Four minutes. The plausible-and-wrong line is worth saying slowly; it is the argument for taking data view configuration seriously rather than treating it as setup. Custom containers get their own slide shortly, so just name them here.

Data views

Include and exclude values

  • Filter a dimension to specific values, or drop specific values, at the data view level.
  • Applies to everyone using the data view, retroactively, without touching the stored data.
  • Common uses: internal traffic, test accounts, a page name that was collected wrongly for two weeks.
  • Document it. A number that cannot be reconciled with the raw data, because of an exclusion nobody recorded, destroys trust quickly.
This is a blunt instrument. Excluding a value makes it invisible to every analyst on that data view, and none of them will know why their total does not match.
Four minutes. The documentation point is the professional one. Tell the story if you have one: an unexplained exclusion is how a team spends a week reconciling two numbers that were never going to match.

Data views

Session settings

  • The inactivity gap that ends a session. Thirty minutes is the common default, not a law.
  • A session can also be forced to start when a chosen metric fires, or when a dimension value changes.
  • Change it and every session count on that data view changes, retroactively.
  • For AcmeHealth, the question worth asking is whether a contact centre call should start a new session at all.
Two data views on one connection can legitimately disagree about how many sessions exist. Neither is broken. They are answering different questions.
Four minutes. Callback to Tuesday. The AcmeHealth question is real: call records arrive as single events, so a naive session rule counts every call as a session and inflates the session counts of exactly the members who were struggling. Worth thirty seconds of discussion.

Data views

Component IDs and portability

  • Every component has a friendly name for humans and an ID for the API, Report Builder and project portability.
  • Give equivalent components the same ID across data views and a project opens correctly on either.
  • Without that, a project built on one data view opens on another and shows nothing.
You have five data views on this connection today plus one each. If your IDs disagree, nothing you built moves between them.
Three minutes. Dry but exam relevant and practically true in the room today. Keep it short.

Data views

Sub-event analysis and custom containers

  • Normally a segment includes or excludes a whole event. Sub-event analysis works on individual objects or arrays inside one event.
  • Define the array as a custom container in the data view, then segment on one element without dragging in the rest.
  • The classic case is a basket: segment on one product without pulling in everything else in the order.
  • Our case is call topic tags. A call tagged with three topics should be countable against one of them without the other two coming along.
This is recent, most of the room will not have seen it, and you will build one this afternoon on data you created this morning.
Four minutes. The basket analogy lands fastest; the topic tag case is the one they build. Do not over-explain here, the lab teaches it. This is a good differentiator slide if anyone in the room has prior Adobe Analytics experience.

Section 2

Turning a transcript into data

The only problem this week that CJA cannot solve on its own.

Divider. Say the subtitle out loud.

The boundary

CJA cannot read your transcript

  • Derived fields operate through a fixed set of functions: case when, classify, lookup, concatenate, math, date math, deduplicate, find and replace, merge fields, split, next or previous, summarize, trim, URL parse, regex replace.
  • There is no language model behind any of them. Regex on a transcript finds the word "frustrated". It does not find frustration.
  • So the sentiment column in the call file is empty, and no setting in this product will fill it.
Scoring text is an upstream job. Data Prep, Data Distiller, a model outside Adobe, or, this morning, you and Copilot. CJA's job starts once the score exists, and it is very good at that part.
Five minutes and be blunt. Vendors and internal teams routinely imply otherwise, and an analyst who promises transcript sentiment inside CJA will be wrong in front of a stakeholder. The honest boundary is also the useful one: it tells them exactly where to spend engineering effort.

The prompt

Why the output contract matters more than the wording

  • Twenty five people are producing rows that have to join on one key in one lookup dataset.
  • So the prompt specifies: one CSV row, no header, no prose, no code fence, columns in a fixed order, enumerated values only, numerics to two decimals.
  • Constrained vocabularies for every categorical field. Free text tags would give us seventy tags from twenty five people.
  • "If you are unsure, choose the closest allowed option" rather than leaving a blank, because a blank breaks the join silently.
The most likely failure this morning is Copilot wrapping the row in a markdown fence or adding a sentence of explanation. The collection sheet catches it. Expect it, and do not let it eat the exercise.
Five minutes. This is a transferable skill well beyond today: anyone building an LLM step into a data pipeline needs an output contract, and most people learn that the hard way. Warn about the fence before they start, not after.

Section 3

Derived fields

Report-time transformation, built in a rule builder, managed at connection level.

Divider.

Derived fields

What a derived field is

  • A new field defined by a sequence of rules over existing schema fields and standard components.
  • Applied at report time, so it works on history immediately and nothing is reprocessed.
  • Defined inside a data view, managed at connection level. Change it in one data view and every data view on that connection sees the change.
  • Available on Select packages and above. We have Prime.
Calculated metric or derived field? A calculated metric combines existing metrics with arithmetic and lives in the rail. A derived field transforms a field's values before anything is counted, and lives in the data view. If you are changing what a value is, it is a derived field.
Five minutes. The callout is the distinction people muddle and the exam tests. The connection-level scope is worth repeating because it bit somebody on Tuesday in every cohort: two analysts, one connection, same derived field name, one gets overwritten.

Derived fields

The rule builder

  • Selector on the left: functions, function templates, schema fields, standard fields. Drag from here.
  • Rule builder in the middle: rules run in sequence, and the last one determines the output.
  • Field settings: name, description, and the resulting data type.
  • Final output on the right: a live preview over the last 30 days of data, updating as you build.
Use the preview constantly. A derived field that returns one value for every row, or blanks for most, is obvious in the preview and invisible once it is in a report.
Five minutes. The live preview is the single most useful part of the interface and people ignore it. Frame it the same way you framed the segment builder's live count on Tuesday: check before you save.

Derived fields

Limits worth knowing before you build

  • Maximum ten schema fields per derived field, of which at most three may come from lookup or profile datasets.
  • Function count limits vary by function. Case when allows five per derived field, concatenate two.
  • 200 operators per derived field. One operator is one criterion with one value, so a case when with many conditions adds up faster than it looks.
  • A maximum number of derived fields per connection, depending on package.
If you are approaching these limits, the answer is usually to chain two simpler derived fields, or to push the logic upstream into a lookup dataset. A monolithic rule block is hard to debug and harder to inherit.
Four minutes. The numbers are exam relevant. The advice in the callout is Adobe's own guidance and it is good engineering practice: people build one enormous case when and then nobody can maintain it.

Derived fields

What belongs here, and what belongs upstream

DERIVED FIELD
Report time, reversible
Bucketing, classifying, combining, cleaning values that already exist. Fast to build, easy to change, applies to history instantly.
LOOKUP DATASET
A joined table
Large classification tables, anything maintained outside CJA, anything produced by a different system. Your scorecard is here.
UPSTREAM
Data Prep, Distiller, ETL
Heavy transformation, anything needing a model, anything that must be identical across multiple tools. Expensive to change.
Cheap and reversible on the left, expensive and authoritative on the right. Start on the left, and move something right only when more than one consumer needs it.
Five minutes. This is an architectural judgement slide and it is the kind of thing that separates a senior practitioner. The heuristic in the callout is worth writing down: build it in the data view until a second team needs it, then promote it.

Section 4

Connections and stitching

How five sources became one person, and what it cost.

Divider.

Connections

What a connection is

  • A set of Experience Platform datasets brought into CJA for reporting. Ours holds eleven.
  • Each dataset is declared as event, profile or lookup. That choice determines how it can be used.
  • Backfill decides whether existing historical data comes in or only new data from now on.
  • Datasets can be added later. The connection does not have to be complete on day one.
The three dataset types are a named exam objective. Event has a timestamp and a person ID. Profile carries attributes about a person. Lookup attaches attributes to a key, like your scorecard this morning.
Five minutes. The three types are explicitly listed in the exam guide, so be precise. Use this morning's scorecard as the lookup example since they built it; a concrete instance beats a definition.

Connections

Per dataset settings

  • Person ID. Which identity this dataset is keyed on. Our web events use the stitched ID, the call file uses the GUID.
  • Timestamp. Which field is the event time. For the membership file it is the enrollment date.
  • Key and matching key for lookup datasets. Our scorecard keys on call ID.
  • Get any of these wrong and the dataset joins to nothing, silently.
A lookup that returns blanks for every row is almost always a key mismatch, not a data problem. Check the key before you check anything else.
Four minutes. The debugging heuristic is the useful part, and somebody in the room probably hit it in the last hour. Ask.

Connections

Adding data later, and guardrails

  • New datasets can join an existing connection, with or without backfill.
  • There are documented limits on datasets per connection, data views per connection and rows per day. They vary by package.
  • Our package is Prime, which allows 750 data views per connection and eight concurrent report requests.
  • That concurrency number is why this room is split across breakout rooms sharing screens rather than twenty five people all querying at once.
If a report spins for a long time today, it is more likely to be concurrency than a broken query. Wait before you rebuild.
Four minutes. Say the concurrency thing plainly, because it will happen and instructors otherwise waste time debugging. It also explains a course design decision, which participants appreciate.

Stitching

The problem stitching solves

  • A member browses AcmeHealth anonymously. The web SDK knows them only as an ECID, a cookie.
  • They register and log in. Now the same events carry a GUID.
  • Every earlier event is still keyed on the cookie. Without intervention, one human is two people in your reports.
  • Stitching rewrites the person ID on the earlier rows so the whole history belongs to one person.
64 percent of our baseline population has anonymous activity before they authenticate. Without stitching, more than half the pre-registration journey is orphaned.
Five minutes. This is Monday's identity lesson made operational. The 64 percent is from the generated data and it makes the abstraction concrete. Everything they have done this week rests on this working, which is worth saying out loud.

Stitching

Field based stitching

  • You nominate an event dataset, a persistent ID (the cookie) and a person ID field on the same dataset.
  • CJA adds a stitched ID column. Where a row has a person ID, it is used. Where it does not, the value is looked up from other rows sharing that persistent ID.
  • If no person ID can be found for a cookie, the persistent ID is used instead, so nothing is lost.
  • Works without the Experience Platform identity graph, which is why it is available from the Select package.
  • Only applies to experience event datasets, and the person ID must appear at least once for each cookie.
One dataset, two columns, no graph. It solves the two ID problem inside a single stream and nothing more.
Six minutes. Teach this first because it is the simpler mental model and because the exam does not know which package a candidate owns. The fallback behaviour matters: unstitched events are not dropped, they are keyed on the cookie, which is why People counts differ between stitched and unstitched views rather than one being empty.

Stitching

Graph based stitching

  • You nominate the event dataset, the persistent ID, and a person ID namespace from the Experience Platform identity graph.
  • CJA queries the graph with the cookie to find the person identity, rather than looking for it on the same dataset.
  • So an identity learned from a different source, a batch file or a mobile login, can resolve web events that never carried it.
  • Requires Prime or above. That is what we have, and it is what is configured on this sandbox.
  • Where the graph returns more than one candidate, the lexicographically first identity is chosen.
Field based asks one dataset what it already knows. Graph based asks the whole platform. Our configuration: persistent ID is the ECID, person ID namespace is the AcmeHealth GUID.
Six minutes. The distinction in the callout is the sentence to remember and the likely exam framing. Both are taught because the exam is package agnostic. State our actual configuration so the next lab makes sense as a thing that was really done to this sandbox.

Stitching

Live, replay, lookback and backfill

  • Live stitching resolves events as they arrive, with whatever the graph knows at that moment.
  • Replay reprocesses recent history at intervals, so events that arrived before an identity was known get re-keyed once it is.
  • The lookback window sets how far replay reaches. Longer catches more delayed logins and costs more processing.
  • Backfill is the one-off reprocessing of history when stitching is first switched on. Its maximum depth depends on package.
Replay is why a member's Monday browsing appears under their name on Tuesday. It is also why enabling stitching is an administrator job done days before a course, not a lab step.
Five minutes. Replay explains something they experienced on Tuesday morning without knowing why, so connect it. The last line sets expectations for the next lab, which is deliberately a comparison rather than a configuration exercise.

Section 5

Data governance

Labels, policies and access. The gap yesterday's curation lesson left open.

Divider.

Governance

Labels: saying what a field is

  • Applied to fields and datasets in Experience Platform, and they travel with the data into CJA.
  • Contract labels for obligations from a data provider. Identity labels for fields that identify a person, directly or indirectly. Sensitive labels for categories needing special handling.
  • Custom labels for anything your organisation cares about that the standard set does not cover.
  • A label is a statement of fact. On its own it changes nothing.
Labelling is the cheap part and it is where most programmes stop. A labelled field with no policy is documentation, not control.
Five minutes. Keep the taxonomy light and the distinction sharp: labels describe, policies enforce. For a health plan the identity labels are the ones that matter most and the room will already have opinions, so leave a little space for them.

Governance

Policies: what the label makes happen

  • A policy says: data with this label may not be used for this purpose.
  • Enforcement happens where the data is used, most visibly at activation and export.
  • Policies are defined centrally, so one team's decision protects every downstream consumer.
  • Violations surface as a blocked action with a stated reason, not a silent failure.
Yesterday you curated a project and a view-only recipient could still export the table. A policy is the control that would have stopped the export. Curation shapes the view; policy constrains the use.
Five minutes. The callback to yesterday's distribution solution is the whole point of putting governance here rather than on Friday. Make it explicitly: the gap they discovered yesterday is closed by this.

Governance

The transcript problem, and the one you made this morning

  • A call transcript is free text a member spoke aloud. It can contain anything they chose to say.
  • It cannot be sampled safely, it cannot be reliably de-identified by rule, and it is extremely useful.
  • This morning you created a second artefact from it: a scorecard containing inferences about a member's emotional state.
  • That derived data may need the same handling as the source, and it is easy to forget because it looks like harmless numbers.
You pasted these transcripts into Copilot because they are fictional. The reason that was acceptable is the reason it would not be with a real member call, and the labels and policies in this section are how an organisation makes that boundary something other than a matter of individual judgement.
Five minutes and it is the most important slide of the afternoon for this audience. Derived data inheriting the sensitivity of its source is the point people miss. Let the room talk; several of them will have a live version of this question at work, and the discussion is worth more than the slide.

Governance

Access control

  • Product profiles in the Admin Console group users and grant permissions.
  • Permissions cover reporting tools, component types, and which data views a profile can reach.
  • Withholding a data view is the blunt and reliable control: no data view, no report, regardless of what was shared.
  • Guided analysis access is granted separately, which is how an administrator can give a stakeholder the guided path without Workspace.
Three controls, three jobs. Curation for clarity, policy for permitted use, permissions for who gets in at all. Using the wrong one is how sensitive data ends up somewhere it should not be.
Five minutes. The three-way summary in the callout is the take-home and it is examinable. The guided analysis permission is a practical tip worth its thirty seconds, since several people will have been wondering how to give stakeholders something safe.
